# Conformance and the Agent Loop
> spec/, cmd/kavach, bench/ — twelve languages held to one contract, and how an agent uses all of it

## One contract, many implementations

Kavach has one replayer and one verifier, both in Go, and twelve SDKs that record and act as hosts: Go, C (with a C++ wrapper), Rust, Haskell, Java, Julia, Python, TypeScript, Ruby, PHP, Elixir and OCaml. Every SDK writes into a recorder written in Go and is driven by a CLI written in Go, so an SDK that is wrong by one byte produces journals the reader rejects or replays that report the wrong status. Nothing about the other languages is checked by reading their code. Instead, `SPEC.md` defines a set of executable **conformance suites**, and an implementation conforms if it passes them.

This chapter covers the versioning rules the suites are tied to, the three suites, how each SDK runs them, and then the user-facing end of the system: the `kavach` CLI, its MCP server, `AGENTS.md`, and the planted-bug benchmark that measures whether variants catch narrow fixes.

## Versioning

@spec 7

In practice this means the format is free to change before 1.0, and the suites are what keep the twelve SDKs in step when it does: a 0.x change regenerates the suites, and every SDK either passes the new ones or does not conform. The Go reader rejects any minor other than the one it implements; `spec/testdata/invalid/newer-minor.kavach` checks that.

## The three suites

@spec 8

The three suites test three different contracts, and each is run against a different part of an implementation:

| Suite | Lives in | Tests | Section |
| --- | --- | --- | --- |
| Golden journals | `spec/testdata/valid`, `invalid` | a journal **reader**: decodes valid files to the expected JSON, rejects invalid ones | §8 |
| Host transcripts | `spec/host/*.jsonl` | a **host**: given driver messages, answers with exactly the expected messages | §9.6 |
| Recorder cases | `spec/recorder/sdk`, `spec/recorder/journal` | the SDK's **recorder half** (frames it writes) and `kavach-recorder` (journals it writes) | §10.6 |

All three follow the same rule: the checked-in files are generated by a program in the repository, and are never edited by hand. A new case is a change to the contract and goes in the same change as the `SPEC.md` text it tests.

### Host transcripts

@spec 9.6

## The twelve SDKs

The suites test the protocols, not SDK code, so they hold a service with no SDK to the same contract. `INTEGRATING.md` defines "done" for such an integration as passing both suites, and `examples/ledger/protocol` is a Julia ledger that writes the frames itself and replays to the same verdicts as the Go demo.

Every SDK has a host, a recorder half, the §9.6 conformance handler, and a test command that runs both its suites. Six of them implement the shared-memory ring of §10.7 (Chapter 4), passing it to the recorder as file descriptor 3 where the runtime can, and by name (`ring_path`, which the recorder unlinks) where it cannot; the other six record over the pipe only.

## AGENTS.md

`AGENTS.md` is the page an AI coding agent reads first; `llms.txt` points to it ("Start with AGENTS.md") and lists the other documents for a model that is indexing the repository. It is not part of `SPEC.md`. It is reproduced here verbatim, with its headings demoted.

#### Using Kavach as an AI coding agent

Kavach gives you an objective check on whether a fix actually fixed a
production incident. Use it instead of reasoning from logs.

A **fixture** (`*.kavach`) is a recording of what a service did before it
failed: every input, every clock and random read, every output, and a marker
saying how it failed. A **host command** starts the service's own build in a
mode where the `kavach` CLI drives it over a pipe, in any language: `./ledger`
for a Go service (its `main` calls `kavach.MaybeReplay`), `python -m ledger`,
`node dist/main.js`. `--bin`, `--old` and `--new` all take a host command; a
string is split into words like a shell would, and `kavach-host` is appended.

#### The loop

1. **Read the incident.**
   `kavach inspect <fixture>` prints each record; add `--full` for the panic
   stack and untruncated data, or `--json` to parse it.
2. **Reproduce it before changing code.**
   `go build -o /tmp/old ./path/to/service`, then
   `kavach replay <fixture> --bin /tmp/old`. Expect `still_failing@N`, where `N`
   is the seq of the input that failed. If replay does not reproduce the
   failure, stop and report that; do not guess at a fix.
3. **Fix the handler.** Change code, never the fixture.
4. **Verify.**
   `go build -o /tmp/new ./path/to/service`, then
   `kavach diff <fixture> --old /tmp/old --new /tmp/new --json`.
   The fix is accepted only when `verdict` is `fixed`. Besides the recorded
   incident, `diff` replays at least 10 **variants** of it (the failing input
   with fields changed or removed, moved earlier, earlier inputs dropped or
   redelivered, the clock shifted) that make the old build fail the same way.
   A fix that only handles the exact recorded input fails one of them.
   If the verdict is `variant_failed(K)@N`, the variant is saved (its path is
   under `variants.checks[].file` in the JSON); reproduce it with
   `kavach replay <variant> --bin /tmp/new` and generalize the fix. Never
   special-case the variant.
5. **Keep it as a regression test.** Copy the fixture into the service's
   `testdata/` and run it with `kavachtest.Run` in a Go test.

#### Verdicts

| Verdict | Meaning | What to do |
| --- | --- | --- |
| `fixed` | The recorded failure is gone, invariants hold, earlier steps match production, and every variant passes. | Done. |
| `variant_failed(K)@N` | The recorded incident passes, but variant `K` still fails at its input `N`. | Your fix is too narrow. Replay the saved variant. |
| `unverified` | The recorded incident passes, but fewer than 10 variants reproduce it on the old build. | Report it; do not claim the fix is verified. |
| `still_failing@N` | The step of input `N` panicked or returned an error. | Keep working. |
| `invariant_violated(X)@N` | Declared invariant `X` broke after input `N`. | Your fix corrupted state. |
| `diverged@N` | A step before the failure produced different outputs from production. | Your fix changed behavior it should not have. |
| `nondeterministic@N` | The handler read time or randomness differently from the recording. | Read time and randomness only through `env`, in the same order. |
| `ok` | The fixture recorded no failure and replay matched. | Nothing to fix. |

`still_failing`, `invariant_violated`, `diverged` and `nondeterministic` from
`diff` refer to the recorded fixture; on a replayed variant they refer to the
variant.

Exit codes: `0` for `fixed` or `ok`, `1` for any other verdict, `2` for usage
errors, `3` when the fixture or binary cannot be used.

#### Rules

- Never edit, regenerate or delete a fixture to make a test pass. A fixture is
  a record of what happened in production.
- Handlers must call `env.Now()`, `env.Read()` and `env.Emit()` instead of
  `time.Now`, `math/rand`/`crypto/rand`, or performing effects directly.
- Report the verdict exactly as Kavach prints it.

#### Over MCP

`kavach mcp` serves the same loop as a Model Context Protocol server on
stdin/stdout. Register it with your client, e.g. for Claude Code:

```bash
claude mcp add kavach -- kavach mcp
```

(This repository's `.mcp.json` does the same with `go run ./cmd/kavach mcp`.)

| Tool | Arguments | Returns |
| --- | --- | --- |
| `kavach_list_incidents` | `dir` (default: working directory) | every `*.kavach` under it, with the recorded failure's kind, seq and message |
| `kavach_replay` | `fixture`, `bin` (default `$KAVACH_BIN`), `include_steps` | `verdict`, `passed`, `detail`, `recorded_failure` |
| `kavach_diff` | `fixture`, `old`, `new`, `variants` (default 10), `keep` | `verdict`, `passed`, the old and new replays of the fixture, `variants` with every check and saved failing variants |

A verdict that is not a pass is a normal tool result; `isError` is set only
when a tool could not run (missing file, a host command that does not start as a host).

The loop is the reason for the verdict design in Chapter 5. Step 2 makes the agent prove it can reproduce before it changes anything; step 4 refuses a fix on the evidence of one input; the rules forbid the one move that makes every check pass trivially, editing the fixture.

## The planted-bug benchmark

`bench/` measures one thing: whether variants reject fixes that handle the recorded incident but not its siblings. It holds ten small handlers, each with one planted bug, a correct fix, and a **narrow** fix written to pass the recorded incident and nothing more. `Mode` selects the build:

| --- | --- | --- |

`BENCHMARKS.md` reports the same: 10 of 10 reproduced, 10 of 10 correct fixes `fixed` (255 of 340 variants reproduce, 25.5 per bug), 10 of 10 narrow fixes rejected, all as `variant_failed`. It is explicit about what this does not show: the bugs and both fixes were written by the project, so the result says variants catch narrow fixes that differ from the correct one along an axis variants perturb (an event type, a field value, the clock, an earlier input); it says nothing about how often an agent's real fixes are narrow in ways no variant reaches, and with each narrow fix run once there is no false-accept rate beyond "0 of 10". It also records that the first draft of the `string-qty` correct fix validated `qty` but not `price` and was rejected by the variant that removes `price`.

`go test ./bench -run EndToEnd -v` (`bench/e2e_test.go`) repeats all ten through real binaries: each bug is built as a service (`bench/cmd/benchsvc`) in three forms, the buggy build records its own fixture, and the CLI inspects, replays, accepts the correct fix, rejects the narrow one, and replays the saved variant against both; then the same verdicts are read back over `kavach mcp`. It builds 31 binaries and is skipped under `-short`.

## Open questions

`SPEC.md` ends with the questions the specification has not settled. They are reproduced verbatim, then checked against the code.

@spec 11

Where they stand today:

| Item | Status in the code |
| --- | --- |
| Starting mid-stream, External queries | Resolved, as marked. |
| Self-replay | **Resolved** in 0.2 by the host protocol (§9). The CLI replays every language, Go included, through `replay.RunHost`; `kavach-replay` appears nowhere in the code. |
| Concurrency inside a step | Open. `kavach.Handler` documents that handlers are called from one goroutine at a time. |
| Sensitive data | Open. Only environment secrets are hashed (form `1`). |
| Recreating the host | Specified in §6.3, not implemented (Chapter 5). |
| Platforms, Local state outside the journal | Open; both depend on sandbox replay. |

| Flags evaluated outside the handler | Open. |
| Reporting compensations | Open. `diff` reports only the first divergence (`replay.Compare`). |
| Large inputs | Open; the 16 MiB record limit stands. |
| Losing the tail | Open. With the ring, published frames survive the service's death as they did in the pipe; the cgroup-wide `SIGKILL` case is unchanged. |
| Pipe cost | **Resolved** in 0.2 by the shared-memory ring, §10.7 (Chapter 4): it replaced the transport and kept the frames. `BENCHMARKS.md` reports 81.2 ns/event over the ring against 493.7 over the pipe on an M3 Pro. |
| Cost of continuous recording | Open. The demo fixture's size (1,954 bytes) is published; real compression ratios and retention are not. |
| Snapshots within a segment | Open. |

## What's next

Two kinds of work are outstanding: measuring whether Kavach helps agents, and a short list of engineering items found in the code.

### An agent benchmark

The planted-bug benchmark measures the verifier with fixes the project wrote. The next step is to measure agents, in the style of SWE-bench. None of this exists in the repository yet; it is the plan.

- **Task set.** Services in several SDK languages, each with a real or planted production bug, its recorded fixture, and hidden tests that a correct fix passes and a narrow one fails. Tasks should include bugs that variants cannot reach (a fix that differs from a correct one only on inputs no mutation produces), so that the benchmark can find Kavach's false accepts rather than only its true rejects.
- **Harness.** Each task is a fresh checkout. An agent runs headless (for example Claude Code in non-interactive mode) with `kavach mcp` registered and `AGENTS.md` in the repository, a fixed budget of turns and time, and no network beyond the model. The harness records every tool call, the final diff, and the agent's claimed verdict.
- **Baseline.** The same tasks and budget with Kavach removed: the agent gets the incident as logs and a stack trace, which is what it would have without a fixture.
- **Reporting.** Per task and in aggregate: whether the final fix passes the hidden tests; whether `kavach diff` called it `fixed`, and how often those two disagree in each direction; how often the agent claimed success without a `fixed` verdict; and cost (turns, tokens, wall time). Each number goes in `BENCHMARKS.md` with the command that produced it, as the existing ones do.

### Engineering items

- **SDK suites in CI.** Only the Go suites run in CI (above). The other eleven SDKs need a Linux job each, which would also exercise the five non-Go rings on Linux.
- **A writer that outruns the recorder.** When the ring is full the SDK rings the doorbell and sleeps until there is room, so a recorder that is starting or descheduled blocks the service. The same TODO is in three SDKs:

@code sdk/go/recorder.go 229-245

  The C SDK's comment names the alternative §3.6 allows: drop the records and mark the gap with a `dropped` marker, instead of blocking.

- **Rotation behind a slow seal.** The recorder's segment rotation (Chapter 3) waits if the previous segment is still being sealed when the next rotation arrives; a third buffer or a backpressure policy is deferred (`internal/recorder/recorder.go`, the TODO above `r.reap(true)`).
- **Huge pages for the ring.** An idea, not yet in the code: back the 8 MiB ring with huge pages to cut TLB misses on the copy into the ring. It interacts with the double mapping of the data area (Chapter 4), which needs both mappings to be aligned to the page size in use.
